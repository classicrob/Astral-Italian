# Native input clock audit (SOL A, PORT/head authorization 2026-10-24)

The frozen M1 diagnostic confirms the functional bug: F at virtual report1858, A/B at1836, flick delayed to1872 (=1836+36 reports). The original 5ms host alarm therefore schedules the spin 180ms after A/B in **wall time**, while Cappy consumes its mod press on a **game frame**. A fast game can advance Cappy before the host-timed spin. A slow server can start Spin before the cap's contact with the identical key script. This is separate from pipeline/cadence tier measurements.

Server and M1 key scripts are identical. First Cappy-state difference for air delays2/4/6 is script frame30 / Cappy frame394: server jumping, M1 grounded until31. Both throw at script40 and release at47; the flight is not earlier on M1. Air spin starts at script54/47/51 on original M1 runs versus42/45/46 on server. Release heights differ because the earlier Spin changes Mario's jump. Original evidence: `m1g/runs/full54-r1-cappy`, `m1g/srv-cappy-54f`, raw shake/KPAD diagnostic `m1g/runs/cappy-timing-diag-r2`.
